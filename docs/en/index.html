Git tag workflow, made reliable

Every release starts with the right tag.

Tagsmith lets your team define the convention, inspect existing tags, and validate version order and format before creating one. Less guesswork; a release trail you can trust.

Get it on npmView on GitHub
# Start in an existing repository
$ tagsmith list
✓ 12 conforming tags · 1 anomaly
$ tagsmith next --level minor
✓ Next tag: v1.4.0
$ tagsmith create --push
✓ Validated and created v1.4.0
Why Tagsmith

Tags are small—until release day makes them a risk.

Manual names, mixed formats, and an ungoverned tag history leave CI, release notes, and collaborators without a common source of truth.

!

Formats drift

`v1.2.3`, `release-1.2.3`, and `final` end up together. Soon nobody knows which tag is a real release.

↗

Version order is guessed

Backfilling history or working in parallel can create a tag below an existing version and break automation.

✓

Problems surface too late

Without local validation, an invalid tag is often found only by CI or another developer after it is pushed.

Four steps

Turn your tag convention into an executable safety net.

Define or infer

Commit `.tagsmith.json`, or start directly from existing SemVer-style tags.

Inspect the history

Sort semantically and flag pattern mismatches, unparseable values, and duplicate versions.

Preview the next release

Calculate the next safe version before changing the repository.

Create after validation

Check format, parseability, strict ordering, and uniqueness before the tag exists.

More than one release stream

Clear rules from one project to many independent tag lines.

SemVer, CalVer, and build numbers

Choose the model that matches your release rhythm. CalVer and build numbers receive the same strict format and ordering checks.

Zero-configuration adoption

Use Tagsmith without a configuration file. It defaults to SemVer and infers common existing patterns, so adoption does not require rewriting history.

Multiple tag lines

Use `--tag` for app, release, or another independent sequence. Each line has its own pattern, model, and push behavior.

Automation and workflow guardrails

`--json` supports CI. Optional merge policies use local git hooks to restrict sources that merge into protected branches.

Quick start

Start in an existing repository with three commands.

All you need is Node.js 18+ and git. You can also install the package as a project dev dependency rather than globally.
