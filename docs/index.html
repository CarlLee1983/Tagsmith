Git tag workflow, made reliable

每一次發版，都從正確的 tag開始。

Tagsmith 讓你定義團隊規格、檢視既有 tag，並在建立前驗證版本順序與格式。少一點猜測，多一點可追溯的發版流程。

在 npm 取得 Tagsmith查看 GitHub
# 在既有 repo 中開始
$ tagsmith list
✓ 12 個合規 tag · 1 個異常
$ tagsmith next --level minor
✓ 下一個 tag：v1.4.0
$ tagsmith create --push
✓ 已驗證並建立 v1.4.0
為什麼需要它

tag 看似小事，卻常在發版時變成風險。

手動命名、不同格式與沒有規則的歷史 tag，會讓 CI、release note 和團隊協作失去共同依據。

!

格式逐漸漂移

`v1.2.3`、`release-1.2.3`、`final` 混在一起，之後誰也無法確定哪個是正式版本。

↗

版本順序靠猜

補歷史 tag 或平行開發時，容易建立小於既有版本的 tag，破壞自動化流程。

✓

推送後才發現

沒有本機驗證，問題通常到 CI 或其他人拉取 tag 後才浮現。

四個步驟

把 tag 規格變成可執行的安全網。

定義或推斷

用 `.tagsmith.json` 固定規格，或直接從既有 SemVer tag 開始。

檢視現況

依語意排序，標出格式不符、無法解析與重複版本。

預覽下一版

在不改動 repo 的前提下，先計算下一個安全版本。

驗證後建立

確認格式、可解析性、嚴格遞增與 tag 唯一性後才建立。

不只一種 release

從單一專案到複數 release line，都有清楚規則。

SemVer、CalVer、build number

選擇符合產品節奏的版本模型；CalVer 與 build number 也同樣受到嚴格格式與順序檢查。

Zero-config adoption

沒有設定檔也能操作。Tagsmith 以 SemVer 預設值運作並推斷常見既有 pattern，讓導入不必先重整歷史。

多條 tag 線

用 `--tag` 操作 app、release 或其他獨立序列，每條線各自有 pattern、版本模型與 push 設定。

自動化與工作流護欄

`--json` 適用於 CI；可選 merge policy 則透過本機 git hook 限制受保護分支的合併來源。

快速開始

在現有 repo，三個指令就能上手。

Node.js 18+ 與 git 即可。不想安裝全域指令也可將套件加入專案 dev dependency。

閱讀完整繁中說明
$ npm install -g @carllee1983/tagsmith

$ tagsmith list
$ tagsmith next
$ tagsmith create --push
